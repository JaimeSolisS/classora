# Classora delivery process

- GitHub Issues are the only active backlog. `_docs/tasks.md` is the archived import source.
- One issue in flight (owner decision 2026-10-21, replacing the two-in-flight overlap approved 2026-10-20): the next issue's engineer starts only after the current issue merges. On the 8 GB machine, two issues in flight queued behind each other's heavy commands and swapped, roughly doubling per-issue time. Each issue has its own branch in its own git worktree (or clone), and gets its own QA PASS and its own merge. A dependent issue branches from its prerequisite's branch and merges `develop` into its branch after the prerequisite lands. On a low-memory machine (8 GB), heavy commands (full test suites, `make e2e`, `make sast`, `make scan-secrets`, image builds) run one at a time across all agents, never in parallel.
- Local runs: engineers and QA use the native local stack by default (shared PostgreSQL from `make db-shared`, an own database from `make db-create`, own ports, own worktree; README "Native local stack"). It has no PgBouncer and no built images, so it is not the reference: the Docker-based CI jobs are the parity check on every pull request, and the Docker stacks (`make dev`, `make e2e`) stay unchanged. Teardown: stop the processes and `make db-drop` the own database.
- PM grooms the issue before engineering starts. Never skip grooming. Role: [`_docs/team/pm.md`](team/pm.md).
- Engineer implements the groomed issue, writes tests, runs the pre-QA checklist (lint, scans and only the tests for what changed; the full suites run on the pull request's CI) and commits on the issue branch. The engineer does not close the issue. Role: [`_docs/team/software-engineer.md`](team/software-engineer.md).
- The orchestrator pushes the branch and opens the pull request to `develop` before QA starts, so CI runs on the commit QA verifies.
- QA verifies each acceptance criterion independently, does not modify code, and posts `QA: PASS` or `QA: FAIL`. QA cites the pull request's CI run for the full suites and does not re-run them locally when CI is green. Role: [`_docs/team/qa-engineer.md`](team/qa-engineer.md).
- On FAIL, the issue goes back to the engineer with the QA comment. The engineer commits the fix on the same branch and the orchestrator pushes it, so CI runs again on the new head. QA re-verifies scoped: the fix, every item marked failed, and anything the fix changed; it cites the new green CI run for the rest.
- The orchestrator (the main session) launches PM, Engineer and QA as subagents. It does not groom, implement or test itself.
- README gate: after every issue, the engineer reviews root `README.md` and reports `README updated: ...` or `README reviewed: no update necessary`. QA verifies the verdict before PASS.
- Branches and pull requests: the engineer commits locally on a branch named `m<milestone>-<nn>-<slug>` (for example `m1-11-security-scanning`). The orchestrator pushes it and opens the pull request to `develop` before QA. It merges only when `ci-required` is green for the pull request's current head commit, QA has posted PASS for that commit (or for an earlier commit, see the next point), and the README verdict is recorded. After the QA PASS and README verdict, the orchestrator enables GitHub auto-merge (`gh pr merge <number> --auto --squash`), so the pull request merges as soon as the required check is green on an up-to-date head; the orchestrator then closes the issue once it has merged. `develop` reaches `main` through a release pull request with the same required check, which the human opens and merges.
- Updating the branch before merge (the ruleset requires it to be up to date with `develop`): if the merge or rebase has no conflicts in files the pull request changed, the earlier QA PASS stands and only a new green `ci-required` run is needed. If conflicts in those files had to be resolved, QA re-verifies the affected items, scoped as after a FAIL.
- Flaky tests: a test that fails and then passes on the same commit without a change gets a GitHub issue on its first sighting. The orchestrator re-runs only the failed job (`gh run rerun <run-id> --failed`), never the whole workflow, and links the flake issue in the pull request. A known flake is never a reason to merge on red.
- CI ([`.github/workflows/ci.yml`](../.github/workflows/ci.yml)) runs on every pull request to `develop` or `main`. Each check is one `make` target, so a red check is reproduced locally with the same command. The API tests run as parallel jobs: `api-unit` (`make test-unit`), `api-migrations` (`make test-migrations`) and `api-integration (K/4)` (`make test-integration SHARD=K/4`, four shards); `ci-required` fails if any of them, or any shard, fails.
- GitHub repository settings are configured by the repository owner, or by the orchestrator only when the owner explicitly authorizes a specific change: the `develop` branch (created from `main`) as the default branch, and one ruleset on `develop` and `main` that allows changes only through pull requests, requires the `ci-required` status check with the branch up to date before merging, and blocks force pushes and deletions. With the owner's authorization (2026-10-20), the orchestrator enabled the repository settings `allow_auto_merge` (GitHub auto-merge) and `allow_update_branch` (the "Update branch" button, `gh pr update-branch`).
- Do not silently add requirements; create a follow-up issue for new scope.
- Release ([spec §10, CI/CD](spec.md#10-system-architecture-decisions)): use pull requests and CI checks before merging. DEV receives approved `develop` merges automatically and PROD (`main`) requires GitHub Environment manual approval; both deployments arrive with M9, so until then merging to `develop` or `main` deploys nothing.
